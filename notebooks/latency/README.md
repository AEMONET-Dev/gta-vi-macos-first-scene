# GTA 第一幕画面为什么要等两三秒

> Historical lab entry. Measurements and corrections are dated below. Unlinked filenames identify local inputs or outputs from that run.

在对话《核验 Antigravity 新方案》恢复人物和街道材质之后，用同一个 1080p 合成入口、Series S 配置、M5 Max 和原生着色器服务复测。默认入口对应程序版本 `b45492b5709c`。本轮的单次纹理优化有明确收益，第一幕完整画面的帧间隔仍在秒级。

## 时间花在什么地方

正式版从第一幕第 +17 帧到第 +40 帧，23 个连续画面间隔中位 **2733 ms**，P95 **4195 ms**。这段包含诊断导出。同期 11 个宿主仪表样本中，提交给 GPU 前的准备时间中位 **1690 ms**，按各样本分别计算后，准备时间占比的中位为 **72%**。10 个完整资源计数窗口里，每帧约有 **20,293 次缓冲区刷新声明、18.77 GB 声明范围**。其中一个 174 MiB 缓冲区每帧刷新约 24 次。纹理每帧检查约 9.24 GB，被判定有变化的纹理范围约 21.15 MB。[正式版逐帧统计](<trace/README.md>)

游戏绘制代码从着色器绑定里拿到允许访问的整个缓冲区，将它登记为待刷新。同一提交中，相交的范围可以合并。游戏发出下一次提交时，渲染器必须让游戏中途写入的字节及时生效。在没有可靠写入记录的路径上，它再次读取这些范围、更新 GPU 使用的缓冲区。纹理也要扫描和比较。每一批命令随后还要等 GPU 完成才能回写给游戏。登记资源范围 (`draw.rs`) · 缓冲范围合并和刷新 (`host.rs`) · 无写入记录时的读法 (`shadow.rs`) · 纹理检查 (`texture.rs`)

## 光照与后端编译

正式版能画出人物和街景，仍有暗脸、过曝背景与蓝白亮斑。对这次正式游戏进程的系统日志核对后，归属它的 98 个 Metal 编译服务进程因 SIGSEGV 退出，D3DMetal 将 84 个不同图形管线标记为空操作。具体着色器名被系统隐藏，还无法把其中某条归到人物光照或车身反射。23 个帧间隔中，17 个没有新的服务崩溃，仍各用 2.07–5.37 秒。原生翻译服务的成功计数只覆盖到翻译完成，后续驱动编译另有结果。[编译服务和驱动记录](<texture/compiler-report.md>) · [逐帧对齐](<../../evidence/latency/texture/compiler-frame-overlap.json>) · 真实游戏窗口 (`window-after-1707.png`)

## 已接通的纹理优化

游戏只载入纹理的部分细节时，候选版直接解码已在内存里的部分，省去分配一整张临时图和额外一次复制。196 种布局组合与原来的输出逐字节一致，4 项 GPU 测试通过。实机出现的两种布局，单次测试分别从 88.89 降至 17.75 微秒、从 111.33 降至 9.69 微秒。这组局部测试使用可校验的合成像素。

正常画质运行时，原版与纹理候选到达第 +20 帧的截图分别用了 48.229 与 48.136 秒。两次镜头、采集间隔、绘制数和后半段系统负载有差异。对近似镜头核过材质、光照与最终画面，人物、衣服和街景都能辨认，最终亮度也有明显差异。整帧提速和逐帧光照的一致性仍未得到证实。人物与材质对照 (`scene-pairs.jpg`) · [源码补丁、局部测试和运行记录](<texture/README.md>)

双击试玩纹理优化 (`试玩第一幕纹理优化.command`) 使用这一项改动。默认的[第一幕画面合成入口](<../../lab/启动 GTA VI 第一幕画面合成.command>) 对应另一个对话交付的正式版本。两者使用同一套图像设置和原生翻译服务。

## 对照方法

其他候选在同一局里每两帧切换一次读法，以 ABBA 或 BAAB 的顺序平衡进场时间。前 8 帧用于预热。游戏真实推进，两个设置的镜头与绘制量仍会变化。记录每次提交和每次画面交付的单调时钟，按交付间隔切割；多个线程重叠的时段只在整帧里计一次。轻量轮次在测量区间关闭游戏的材质与截图导出，同时从 macOS 直接抓该次游戏的真实窗口验证。栅栏等待指 CPU 等待本批工作完成，显示器发光时间和纯 GPU 核心运算时间没有直接计量。[计时解析与单元测试](<trace/README.md>) · [对照程序补丁](<../../patches/history/latency/hot/instrumented-v2/b454.patch>)

Gemini 在先前分支观察到，减少搬运的字节数后，如果仍需分段检查每份数据，耗时可能反而增加。本轮按真实游戏的实际写入量、单次刷新耗时与整帧耗时分别验证。[Gemini 的早期实测记录](<../early/第一幕渲染管线拷贝优化对照.md>)

### 关闭游戏内图像导出后的复测

反序对照里沿用原缓冲读法的 16 个帧间隔平均 **2612.48 ms**，中位 **2483.30 ms**。同一组帧按互不重叠的墙钟时间取平均，缓冲刷新 **1291.78 ms**、纹理表准备 **450.15 ms**、其他提交前准备约 **250.40 ms**，合计 **1992.33 ms（76.3%）**。提交到 GPU 完成 **466.87 ms**，其中调用提交函数本身约 **0.60 ms**，等完成信号约 **453.51 ms**。回写约 **125.79 ms**，其余约 **27.5 ms**。这组专用程序两种读法都使用优化后的驻留纹理路径。42 个连续交付区间内，游戏没有导出诊断图片。[逐帧时间线](<../../evidence/latency/runs/xmem-baab-kl4wv5zg/render.json>) · 该轮实际窗口 (`window-after-1633.png`)

### 同一进程里的候选方案

| 试验 | 原读法或原顺序 | 改动后 | 观测 |
| --- | ---: | ---: | --- |
| 上传批次先安排最大任务，整帧中位 | 2550 ms | 3153 ms | 14 / 16 帧，开启组绘制数量更高 |
| 174 MiB 逐页比较，ABBA 单次刷新中位 | 5.982 ms | 6.399 ms | 开启组实际存入 0.844 GB，请求 62.216 GB，337 / 341 次成功使用新路径 |
| 同一缓冲反序 BAAB 单次刷新中位 | 5.920 ms | 6.089 ms | 416 / 416 次成功，存入 0.099 GB，请求 75.900 GB |

缓冲新读法先比对来自同一游戏物理分配的独立映射，只有有差异的 4 KiB 区块才会被写入。这两轮的单次中位均变慢。整帧中位在正序时从 2800 到 2601 ms，反序时从 2483 到 2716 ms，方向相反。这些变化不足以作为对正式版的提速承诺。只追这块资源也只能触及总准备时间的一部分。[上传顺序对照](<../../evidence/latency/runs/schedule-ornp07qk/render.json>) · [逐页比较正序](<../../evidence/latency/runs/xmem-abba-usxk0alo/render.json>) · [反序](<../../evidence/latency/runs/xmem-baab-kl4wv5zg/render.json>)

要接近 30 FPS 的 33.3 ms，应从产生写入的地方记录被改写的物理区块，覆盖同一物理数据的不同映射、流式载入与 GPU 回写，让每次提交按这段时间内的变化更新。对来源不明的写入保留全量校验；过早忽略同一帧内的二次写入会读到旧材质。即使消除了这部分 CPU 工作，本轮等待 GPU 完成的时间仍远超 33.3 ms，还需要处理提交之间的同步与资源复用。已有写入追踪在真实地址映射上的限制 (`cross.log`) · [开源方案的实测边界](<../forks/README.md>)

压缩同一提交内的重叠写前快照也做了单独实测。只按真正有快照要拍的帧分组，关闭时 14 帧的快照耗时中位 66.19 ms，开启时 12 帧为 63.54 ms，完整画面分别为 2800.03 和 2817.04 ms。各帧覆盖的声明数不同，这一差距不足以确认整帧改善。试玩入口只启用已做逐字节校验的纹理优化。[快照交替实测](<../../evidence/latency/runs/snapshot-abba-ge6w564l/render.json>) · [四轮时序汇总](<../../evidence/latency/trials.json>)

本机可运行 `python3 first-scene-latency/summarize_trials.py` 从原始游戏日志重算交替实验。试玩入口运行核验 (`verified.json`) 记录了由正常入口实际加载的程序路径、其 SHA-256 和退出状态，与独立的 220 秒入场实测一致。
