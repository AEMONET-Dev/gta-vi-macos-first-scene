## 改动与证据

`streamed/work` 是 `install.py` 应用光影补丁后的源码。实验复制这份源码，只改 `victory-formats` 与 `victory-gpu` 的纹理代码。[resident-mip.patch](<../../../patches/history/latency/texture/resident-mip.patch>) 可在该源码副本上 `git apply`。Windows 候选程序在 `build/x86_64-pc-windows-gnullvm/release/victory.exe`，SHA-256 为 `3871f42fc179b4e2e1a48a51a4c75a784e15aafc381d5fe4ff7899432fc905f0`。

游戏按需载入纹理时，一些高级细节还缺页，较低分辨率级别已经可读。原先每次载入有变化的这类纹理，会分配一个零填充的整张纹理缓冲区，再把可读部分复制到里面，最后只解码那部分。候选版验证当前级别的地址范围后直接读取原来的字节，输出仍由同一套排布代码生成。此前已经上传的细节得以保留。通常的整张纹理路径继续使用原来的处理方式。

| 实际运行见到的纹理布局 | 整张 / 可读字节 | 旧流程 | 直接读 |
| --- | ---: | ---: | ---: |
| 2048 × 512，8 级 | 1409024 / 360448 | 88.89 µs | 17.75 µs |
| 512 × 1024，8 级 | 700416 / 176128 | 111.33 µs | 9.69 µs |

这是 GPTK/Rosetta 下两种已记录布局的 CPU 微基准，使用确定性的测试字节。同一进程中每种交替测 40 批，每批 8 次。完整图像、采集、提交与 GPU 执行不在测量范围内。基准还对 196 种排布、尺寸、格式与 mip 组合比较两条路径的逐字节输出和每块坐标的预期内容，检查行对齐填充、缺少一字节时的拒绝，以及已上传高级细节。原始结果在 resident.log，用 `python3 check.py` 复测。

光影版的 `material_light.rs` 会将材质颜色、HDR 强度与屏幕深度合成，对有几何覆盖的像素取消原先的加亮项。在另一个线程选出的同镜头位置，固定区域的亮点像素从 174 降到 0。但正式录像的第 1635 帧和 1639 帧在同一区域仍有 323、301 个命中，移动镜头和场景本身的亮物都会影响这个指标。纹理加速保留该合成公式。更细的即时光照与阴影质量，需要检查游戏实际传给光照阶段的输入和按视图绑定的 HDR 资源。参见 `../../tmp/material-input-zPOxz5eq/shot-comparison.json` 和 `spot-statistics.json`。


## 两个实机版本对照

正式版首次进入场景是第 1609 帧，纹理版是第 1726 帧。对齐人物举手的镜头后，正式版第 1632 帧与候选版第 1750 帧里的皮肤、手、衣服、街道路标、店铺和背景建筑仍可辨认。同期材质图亮度平均为 45.9 和 46.8（0–255），在去掉外围边缘的小图上，亮度相关系数为 0.737。实际成像平均亮度为 34.1 和 69.0，人物和背景明显变亮。拍摄时相差一个场景帧，人物姿态、游戏光照输入和背景可见区域也不同，因此这张图不能证明逐像素相等，也不足以把亮度差归因给纹理读取。街景截图两边都可见建筑和地面，机位不同。旧版的蓝白亮斑在两次运行均出现，正式版第 1639 帧与纹理版第 1774 帧在固定区域分别命中 301、341 个像素。完整对照见 带标签的配对小图 (`scene-pairs.jpg`) 和 原始图地址与指标 (`scene-comparison.json`)。

两次整场景帧时没有给出稳定的加速证据。候选版的后半段有一个独立测试进程占用约一个 CPU 核，同期的采图次数与镜头也不同。正确的提交代价仍以缓冲区准备最高。四个项目自带 GPU 纹理用例均通过，包括真实显存上传、移除与恢复细节级别、暂时不可读和重新载入，详见 gpu-tests.log。`check.py` 复测局部速度，`compare_scene.py`（依赖 Pillow 和 NumPy）可从现有实机截图和日志重建对照。

系统日志还确认三轮均有 Metal 编译服务崩溃和 D3DMetal 将部分图形管线设为无操作。正式版的 23 个实测呈现间隔中，17 帧没有新的编译服务崩溃，但全部仍超过两秒。[按进程与逐帧核对的证据](<compiler-report.md>)
