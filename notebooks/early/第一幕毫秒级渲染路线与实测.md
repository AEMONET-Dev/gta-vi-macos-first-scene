# 第一幕毫秒级渲染路线与实测

> Historical lab entry. Measurements and corrections are dated below. Unlinked filenames identify local inputs or outputs from that run.

第一阶段以正常第一幕画面连续运行 30 FPS 为目标，每帧预算 33.3 ms。第二阶段为 60 FPS，每帧预算 16.7 ms。上次固定设置对照的平均帧耗时为 3,509 ms，第 95 百分位为 4,967 ms。仅把平均值降到两个目标就分别需要约 105 倍和 211 倍的提速。[第一幕逐帧记录](<../../evidence/early-submit/frame-times-final.json>)

## 优先改造的游戏资源

在第一幕相对第 8 至 30 帧内，11 条采样都记录了同一块 174 MiB 映射缓冲。它的整块读取次数中位数为每帧 24 次，逻辑搬运量约 4.38 GB，单这项的计时中位数约 147 ms。整帧缓冲搬运量中位数为 19.55 GB。这个资源适合作为第一个迁移对象。先检查它在真实场景中的物理分页、连续区间及读写归属，再选定可以共同迁移的生产和消费步骤。实机日志 (`victory-run-picture-20261125-060048-a0fdsbnh`) · [各阶段统计](<../../evidence/early-submit/stages-to-30.json>)

让 Wine 和 Metal 持有同一份底层存储，用资源编号、偏移、映射版本及 GPU 完成序号约定何时可以使用和复用。线性缓冲可先接入，游戏把同一地址重新映射到其他页面时，应传递新版本。旧版本要保留到使用它的最后一条 GPU 命令结束。同一消耗链中如果还需要由 D3D12 读取结果，也要计入互操作或显式回拷的成本。游戏内存映射实现 (`xmem.rs`) · 现有 GPU 提交实现 (`host.rs`)

每帧另要检查约 12.65 GB 纹理，其中约 94 MB 所属纹理被判定发生变化。纹理的布局转换需单独处理。可从有明确生产者的资源入手，在写入或重新映射时更新。可以在 GPU 上直接处理的纹理，将布局转换也留给 GPU。对仍由游戏线程自由写入的映射，保留可核验的读取路径。实机上通过第二个映射写入后，两个地址的 Windows 写入历史都不可查询。另一次实验中，写入并刷盘后，macOS 报页面干净，读出的内容已经改变。Windows 双映射测试 (`capability.log`) · Wine 与 macOS 对照 (`cross.log`)

## 已在 M5 Max 上跑通的部分

Wine 通过文件映射写入 16 MiB，原生 Metal 直接引用同一批页。GPU 每轮原地更新 4,194,304 个整数，Wine 对全部结果逐字核对。资源和管线预先建立，10 轮预热，80 轮计时。下表中的往返从发出命令计到 Wine 看到完成。GPU 时间取自 Metal 命令缓冲。测量结果 (`results.json`) · 复现脚本 (`run.py`)

| 实验口径 | 中位数 | 第 95 百分位 |
| --- | ---: | ---: |
| 发出请求至结果可见 | 0.266 ms | 0.279 ms |
| GPU 执行 | 0.088 ms | 0.089 ms |
| 包含 CPU 写满缓冲、GPU 执行和 CPU 全量校验 | 2.191 ms | 2.275 ms |

另做了 90 轮双缓冲验证。Wine 在同一虚拟地址交替映射两块不同的底层存储，完成了 89 次重新映射。每轮检查写入地址、另一个映射地址以及未参与本轮计算的另一块缓冲，所有数据正确。独立的反向测试故意漏写最后一个整数，校验在第一轮准确报错。这些实验覆盖了线性缓冲和一段计算。重映射结果 (`results.json`) · 漏写校验 (`negative-control.log`)

## GPU 工作与验收

第一幕每帧约 33 次提交，提交和等待合计的采样中位数为 479 ms。此前同机 Metal 时间线还测到，四个很慢的提交分别有 360 至 388 ms 与 GPU 计算重叠。资源常驻解决了 CPU 搬运后，仍需优化其中两道间接计算。对没有游戏侧读回依赖的批次，可以让 CPU 继续录制下一批，同时用完成序号保护命令分配器、描述符和上传缓冲。游戏要读回结果或等待完成信号时，按原顺序兑现。原生 Metal 追踪 (`native-compute-windows.csv`) · [两道计算的定位](<第一幕原生曝光与慢提交实测.md>)

本轮用隔离的材质启动会话抓到了第一幕实际绑定的两道慢计算。以现有渲染器翻译出的 DXIL 为输入，两个程序都在本机成功转换成 Metal 库、加载，并创建了原生计算管线。针对 `8bbcbda6008eaa37` 和 `c7feccae4e01e454`，下一项最小实验是记录一次游戏派发的真实输入、输出、两张资源表、采样器和间接派发参数，分别用现有路径和 Metal 执行，逐项比对输出，并测 GPU 设备时间。本轮完成了管线创建，游戏数据上的执行和结果对照仍待验证。当前正式启动器的原生服务负责着色器翻译，绘制仍走 D3D12。本轮游戏日志 (`victory-run-picture-20261125-061652-zyrn_xbr`) · 原生建管线实测 (`probe.log`) · 资源绑定记录 (`bindings.json`)

第一项游戏内验收是在相同输入下逐次核对原有路径和原生路径的输出，确认目标资源重复全量上传为零，并记录其余回拷。整帧验收应继续使用实际材质启动器，固定场景和设置，记录平均、第 95 百分位、最慢一帧、绘制丢弃数和实际截图。先观察稳定世界画面，再单列首次着色器编译与资源流入造成的卡顿。
